# 上位銘柄の含み益検証・住所精度改善手順

ランキング上位から順に、土地の含み益が正当かチェックする。
住所解決タグ（`muni_centroid` / `oaza_chome`）に関係なく、ランキング上位から検証し、**必ず** `address_overrides.yaml`（またはパッチファイル）に番地レベル住所を登録する。

## 0. 事前準備

`data/output/ranking_market_cap_ratio.md` が無い場合は、先に生成する：

```bash
python rank_market_cap_ratio.py
```

## デフォルト対象の選定

引数 `$ARGUMENTS` が**指定されていない場合**、以下の手順で対象1銘柄を自動選定する：

1. `data/output/ranking_market_cap_ratio.md` を読み込む（未生成なら `python rank_market_cap_ratio.py` を先に実行）
2. `config/address_overrides.yaml` を読み込み、既に全事業所が登録済みの企業をスキップする
3. ランキング上位から順に、**まだ全事業所の登録が完了していない最上位1銘柄**を対象とする
4. 該当なしの場合はその旨を報告して終了する

引数として証券コードが指定された場合はその企業のみを対象とする。

## パッチモード（並行実行時）

`$ARGUMENTS` に `config/address_patches/` で始まるファイルパスが含まれている場合、**パッチモード**で動作する。これは `parallel_resolve_address.ps1` による並行実行時に使用される。

**パッチモードの動作:**

- **`address_overrides.yaml` を直接編集しない**
- 調査結果を指定されたパッチファイル（例: `config/address_patches/1234.yaml`）に同じYAML形式で書き出す
- 対象証券コードのエントリのみを含める
- セクション6（反映と検証）はスキップする（呼び出し元が `merge_address_patches.py` で一括処理する）

**パッチモードでないとき（通常モード）:**

- 従来通り `config/address_overrides.yaml` に直接追記する

> **重要**: パッチモードでは、調査結果を**必ず**パッチファイルに書き出すこと。ファイルが書き出されなければリサーチ結果が失われる。

---

## 1. 目的

ランキング上位銘柄について、推定土地時価が正当かを検証し、全事業所の住所を番地レベルで特定して登録する。

### よくあるパターン（過大評価の原因）

- **複数拠点の合算:** 事業所名が「本社他」「本社及び工場」等で、複数箇所の土地面積が1行に合算されている
  - 全面積が高地価地点（港区・千代田区等）に紐づくが、実際は一部の土地が郊外にある
  - 例: 「本社他 27,000m²」→ 本社は港区（5,000m²）、倉庫は大田区城南島（22,000m²）
- **面積と立地の不整合:** 都心で1万m²超の土地は不自然（工場・倉庫なら工業地帯が妥当）
- **住所精度が低い:** `muni_centroid` / `oaza_chome` で高地価地点の地価が適用されている

## 2. 対象の特定

### 2.1 対象企業の決定

**引数なし（デフォルト）の場合:**

`data/output/ranking_market_cap_ratio.md` のMarkdownテーブルを読み込み、ランキング上位から順に最上位1銘柄の証券コードを取得する。

テーブルの形式:
```
| 順位 | 証券コード | 企業名 | ... | 住所解決タグ | タグ件数 | ... |
```

**引数ありの場合:**

`$ARGUMENTS` の先頭トークンを証券コードとして使用する。

### 2.2 対象事業所の抽出と分析

対象企業が決まったら、`data/output/{証券コード}_output.csv` を読み込み、**全行**を確認する。

```bash
cat data/output/9351_output.csv
```

各事業所について以下の観点でフラグを立てる：

| フラグ | 条件 | 意味 |
|--------|------|------|
| 合算疑い | 事業所名に「他」「及び」「等」を含む | 複数拠点が1行に合算されている |
| 面積異常 | 都心住所なのに面積 ≥ 10,000m² | 立地と面積が不整合 |
| 低解像度 | 住所解決レベルが `muni_centroid` or `oaza_chome` | 番地特定で精度向上の余地あり |

## 3. Web調査の手順

### ステップ1: 有価証券報告書の原文確認

```
検索: "{企業名} 有価証券報告書 設備の状況"
```

EDINETで原本PDFの**設備の状況**テーブルを直接確認:

- 事業所名に「他」「及び」が含まれていないか（複数拠点の合算サイン）
- 注記欄に「上記には○○を含む」等の記載がないか
- 面積の内訳が脚注に書かれていないか

### ステップ2: 企業公式サイトで拠点一覧を特定

```
検索: "{企業名} 拠点一覧"
検索: "{企業名} 事業所 所在地"
検索: "{企業名} 会社概要 アクセス"
検索: "{企業名} グループ会社 所在地"
```

公式サイトの「会社概要」「拠点紹介」「アクセス」ページで**全拠点の住所を番地レベルで収集**する。

### ステップ3: 個別拠点の住所を番地レベルで特定

```
検索: "{企業名} {拠点名} 住所"
検索: "{企業名} {拠点名} アクセス 地図"
検索: "{企業名} 本店所在地"
検索: "{企業名} 法人番号"  → 国税庁サイトで本店所在地
```

Google Mapsで施設名を直接検索するのも有効。

### ステップ4: 面積の妥当性チェック（合算疑いの場合）

```
検索: "{企業名} {拠点名} 工場 敷地面積"
検索: "{企業名} {拠点名} 倉庫 規模"
```

- 工場・倉庫の敷地面積がプレスリリースや IR 資料に載っていることがある
- 「本社他」の合計面積から各拠点の概算面積を逆算する
- 都心で大面積 → 実際にそんな広い土地があり得るか検証

### 3.5 住所の検証

取得した住所が正しいか、以下の観点で検証する：

1. **区市町村の一致** — 有報の `location_short` と同じ区市町村か
2. **事業所名との整合性** — 工場なら工業地帯、本社なら商業地域にあるか
3. **番地の具体性** — 「○丁目○番○号」または「○-○-○」まで特定できているか
4. **複数ソースでの裏付け** — 2つ以上の情報源で同じ住所が確認できるか
5. **住所の新しさ** — 移転していないか（有報の事業年度と比較）

### 3.6 住所の正規化

`address_overrides.yaml` に登録する前に、住所を以下の形式に正規化する：

```
東京都{区市町村}{町名}{丁目}{番}{号}
```

- 全角数字 → 半角数字（例：「３丁目」→「3丁目」）
- 漢数字 → アラビア数字（例：「三丁目」→「3丁目」）
- ハイフン形式も可（例：「東京都港区六本木3-4-33」）
- 郵便番号は含めない
- ビル名・階数は含めない（土地のジオコーディングには不要）
- 「東京都」から始めること

**良い例:**
```
東京都中央区日本橋1丁目15番3号
東京都港区六本木3-4-33
東京都足立区千住橋戸町31番
```

**悪い例:**
```
中央区日本橋1-15-3          # 「東京都」が無い
東京都中央区日本橋           # 番地が無い（oaza_chomeにしかならない）
〒100-0001 東京都千代田区... # 郵便番号が含まれている
東京都港区六本木ヒルズ       # ビル名で番地が無い
```

## 4. 判定

検証結果に基づき、各事業所について以下のいずれかに判定する：

| 判定 | 説明 | アクション |
|------|------|-----------|
| **住所改善** | 番地レベル住所を特定できた | → セクション5でYAML登録 |
| **確認済み（問題なし）** | 既に `gaiku` で住所も正確 | → 既存オーバーライドがなければYAML登録 |
| **過大評価の疑い** | 合算・面積不整合が確認された | → 代表住所をYAML登録 |

> **重要**: 調査した事業所の住所は、既に `gaiku` レベルであっても、**必ず** YAML に登録する。これにより、今後のパイプライン実行でも一貫した結果が得られる。

### 判定フローチャート

```
対象企業の全事業所を確認
  │
  ├─ 事業所名に「他」「及び」→ 合算の疑い
  │   └─ 原本PDF確認 → 拠点分解 → 個別住所特定
  │       └─ 代表住所をYAML登録
  │
  ├─ 面積≥10,000m² かつ都心住所 → 立地の妥当性確認
  │   └─ 工場/倉庫なら工業地帯が妥当 → 正しい住所をYAML登録
  │
  ├─ 住所解決レベルが muni_centroid / oaza_chome → 番地特定
  │   └─ 番地付き住所をYAML登録
  │
  └─ 上記に該当しない → 現在の住所をそのままYAML登録
```

## 5. 調査結果の保存（YAML登録）

**このセクションは必ず実行する。** 調査結果は YAML に書き出さなければ失われる。

### 5.0 出力先の決定

| モード | 条件 | 出力先 |
|--------|------|--------|
| 通常モード | パッチファイルパスの指定なし | `config/address_overrides.yaml` に直接追記 |
| パッチモード | 引数に `config/address_patches/*.yaml` を含む | 指定されたパッチファイルに出力 |

**パッチモードの場合**: 以下の5.1〜5.3の手順に従うが、出力先を指定されたパッチファイルに置き換えること。パッチファイルには対象証券コードのエントリのみを記載する。

### 5.1 ファイル構造

出力先ファイルに以下の形式で追記（パッチモードでは新規作成）する：

```yaml
# 証券コード:
#   事業所名: 東京都...（フルアドレス）

'1945':
  本社他: 東京都中央区日本橋茅場町1丁目3番1号
'4116':
  東京製造事業所: 東京都足立区宮城1丁目35番18号
'4619':
  本社 他: 東京都北区王子5丁目2番1号
```

### 5.2 登録ルール

- **事業所名は出力CSVの値と完全一致させる**（スペース含む）
  - 例: 出力CSVが「本社 他」なら、YAMLのキーも `本社 他` にする
  - 例: 出力CSVが「本社他」なら `本社他` にする
- **証券コードはクォート付き文字列として記載**（先頭ゼロがある場合に備えて `'1234':` の形式）
- **1企業あたり複数事業所の登録可能**
- **対象企業の全事業所を登録する**（低解像度でない事業所も含む）
- **既存のオーバーライドは上書きしない**（意図的な修正の場合を除く）

### 5.3 登録前のジオコード検証

登録する住所が実際に `gaiku` レベルでジオコーディングできるか確認する：

```python
from src.geocode_tokyo import TokyoGeocoder

geocoder = TokyoGeocoder(
    oaza_csv="data/geocoding/geocode_ref_oaza_chome_tokyo_2024/13_2024.csv",
    gaiku_csv="data/geocoding/geocode_ref_gaiku_tokyo_2024/13_2024.csv",
)

addr = "東京都足立区宮城1丁目35番18号"
lat, lon, level = geocoder.geocode(addr)
print(f"{addr} → {level} ({lat}, {lon})")
# 期待: "gaiku" と表示されること
# "oaza_chome" でも muni_centroid からの改善になる
```

- `gaiku` が得られればベスト（補正係数 1.00）
- `oaza_chome` でも `muni_centroid` からの改善になる（補正係数 0.85 → 0.95）
- `muni_centroid` のままなら住所が不正確な可能性 → 再調査

**全住所のジオコード結果を確認してから YAML に書き出すこと。**

### 5.4 YAML書き出し実行

検証が完了したら、出力先ファイルに書き出す。

**通常モードの場合:**

1. `config/address_overrides.yaml` を読み込む
2. 対象証券コードのエントリを追加・更新する
3. ファイルを保存する

**パッチモードの場合:**

1. 指定されたパッチファイル（例: `config/address_patches/1234.yaml`）を新規作成する
2. 対象証券コードのエントリのみを記載する
3. ファイルを保存する

> **確認**: YAML書き出しが完了したら、ファイルの内容を `cat` で表示して正しく書き出されたことを確認する。

## 6. 反映と検証

> **パッチモードの場合**: このセクションはスキップする。パッチファイルのマージは呼び出し元の `merge_address_patches.py` が行う。

### 6.1 パイプライン再実行

オーバーライド登録後、対象企業の出力を削除してパイプラインを再実行する：

```powershell
# 対象企業の出力CSVを削除（例: 証券コード 4116）
Remove-Item data/output/4116_output.csv -ErrorAction SilentlyContinue

# 再実行
python run.py

# ランキング再生成
python rank_market_cap_ratio.py
```

### 6.2 結果の確認

再実行後、出力CSVで以下を確認する：

1. **住所解決レベル** — `gaiku` または `oaza_chome` に改善されたか
2. **住所取得元** — `override` になっているか
3. **住所解像度補正係数** — 1.000000（gaiku）または 0.950000（oaza_chome）に変わったか
4. **異常値警告** — 警告が消えたか
5. **推定土地時価** — 合理的な範囲に収まっているか

### 6.3 コミット

変更を確認したら、`address_overrides.yaml` の変更をコミットする：

```bash
git add config/address_overrides.yaml
git commit -m "Add address overrides for improved geocoding accuracy

- Verified and registered addresses for top-ranked companies
- Addresses verified via corporate websites and public records
- Improves geocoding accuracy and land value estimation"
```

## 7. 注意事項

- **集約名の事業所**（「本社他」「本社・○○」「○○等」）は、複数の土地が1行に集約されている。代表的な住所（通常は本社住所）を設定する。ただしこの場合、集約されている他の土地とは異なる場所の地価が適用される点に留意する。
- **移転情報に注意** — 検索で見つかる住所が最新でない場合がある。有報の事業年度末時点の住所であることを確認する。
- **Web自動取得のスコアが低かった理由** — `住所取得元` が `securities_report` の場合、Web自動取得（`web_address_research.py`）が試行されたがスコア40未満で不採用になった可能性がある。`data/cache/web_address/resolve_cache.json` で該当キーを検索すれば、試行結果を確認できる。
- **ジオコーディング参照データの範囲** — `data/geocoding/` の参照CSVは東京都2024年版。参照データに存在しない新しい街区番号の場合、番地付きでも `oaza_chome` にフォールバックする。この場合は改善の余地がない。
