引数から以下のパスが導出される：

## 事前検証フラグ

`parallel_research.py` が事前に `config/address_patches/{証券コード}.precheck.json` を生成し、プロンプトに注入済み。
この JSON は `_codex_precheck.py` の出力で、各事業所の自動判定結果を含む。
以下のフラグを参照して調査の優先度付けに使用する。

**フラグの解釈:**

| フィールド                   | 意味                                           |
| ---------------------------- | ---------------------------------------------- |
| `all_gaiku`                  | 全事業所が `gaiku` レベルで解決済み            |
| `has_risk`                   | BAD_PATTERN_1 リスク（合算疑い）がある         |
| `sites[].bad_pattern_1_risk` | 合算名 or 都心高面積 → 重点調査が必要          |
| `sites[].has_override`       | 既に `address_overrides.yaml` に登録済み       |
| `sites[].has_hoka`           | 事業所名に「他」「及び」等の複数所在地シグナル |
| `docs_exists`                | `split-address/{code}.md` が既に存在する（調査済み） |

**調査の優先度:**

- `bad_pattern_1_risk=true` の拠点 → **重点調査**（セクション3の全ステップを実行）
- `all_gaiku=true` かつ `has_risk=false` → 合算リスクなし。現住所をそのまま確認してパッチに登録（Web調査は省略可）

## 1. 目的

指定企業について、合算された土地（BAD_PATTERN_1）を分割し、各拠点の住所を特定してパッチファイルに登録する。

### <a id="bad-pattern-1"></a>BAD_PATTERN_1: 複数拠点の合算

- **複数拠点の合算:** 事業所名が「本社他」「本社及び工場」等で、複数箇所の土地面積が1行に合算されている
  - 全面積が高地価地点（港区・千代田区等）に紐づくが、実際は一部の土地が郊外にある
  - 例: 「本社他 27,000m²」→ 本社は港区（5,000m²）、倉庫は大田区城南島（22,000m²）
- **面積と立地の不整合:** 都心で1万m²超の土地は不自然（工場・倉庫なら工業地帯が妥当）

## 2. 対象事業所の抽出と分析

`data/output/{証券コード}_output.csv` はプロンプトに注入済み。**全行**を確認する。

各事業所について以下の観点でフラグを立てる：

| フラグ   | 条件                                 | 意味                          |
| -------- | ------------------------------------ | ----------------------------- |
| 合算疑い | 事業所名に「他」「及び」「等」を含む | 複数拠点が1行に合算されている |
| 面積異常 | 都心住所なのに面積 ≥ 10,000m²        | 立地と面積が不整合            |

## 3. Web調査の手順

### ステップ1: 有報「設備の状況」の確認

有報PDFから抽出した全拠点データ（事業所名・所在地・土地面積・簿価）が `_sites.json` としてプロンプトに注入済み。
また、有報「設備の状況」セクションのページテキスト全文（注記・面積内訳を含む）が `_facilities_text.txt` として注入済み。「上記には○○を含む」等の注記はこのテキストを参照すること。

以下を確認する:

- 事業所名に「他」「及び」が含まれていないか（複数拠点の合算サイン）
- `location_has_hoka: true` のフラグが立っていないか

### ステップ2: 企業公式サイトで拠点一覧を特定

```
検索: "{企業名} 拠点一覧"
検索: "{企業名} 事業所 所在地"
検索: "{企業名} 会社概要 アクセス"
```

公式サイトの「会社概要」「拠点紹介」「アクセス」ページで**全拠点の住所を番地レベルで収集**する。

### ステップ3: 個別拠点の住所を番地レベルで特定

```
検索: "{企業名} {拠点名} 住所"
検索: "{企業名} {拠点名} アクセス 地図"
検索: "{企業名} 本店所在地"
検索: "{企業名} 法人番号"  → 国税庁サイトで本店所在地
```

### ステップ4: 面積の妥当性チェック（合算疑いの場合）

```
検索: "{企業名} {拠点名} 工場 敷地面積"
検索: "{企業名} {拠点名} 倉庫 規模"
```

- 工場・倉庫の敷地面積がプレスリリースや IR 資料に載っていることがある
- 「本社他」の合計面積から各拠点の概算面積を逆算する
- 都心で大面積 → 実際にそんな広い土地があり得るか検証

### ステップ4.5: 分割面積 (`area_m2`) を推定する（新運用）

- 東京側エントリの面積 (`area_m2`) を `0.0` に固定することは原則禁止する。可能な限り推定値を入れる。
- 推定時は `area_m2_is_estimated: true` とし、`area_m2_source` を必須で記録する。
- 根拠探索の優先順位は以下:
  1. 登記簿（地積）— 法務局の登記情報提供サービスや不動産登記の地積情報を検索
  2. 有報の固定資産注記・設備注記（面積内訳）
  3. 公示地価標準地の近傍地積による推定
  4. Google Maps 衛星写真からの面積測定（Playwright で実施）
  5. 不動産取引価格情報（国土交通省 不動産情報ライブラリ reinfolib）

#### 4.5a: 登記簿・不動産登記の地積情報

Web検索で地積が見つからない場合、以下を試す:

```
検索: "{地番}" "地積" OR "㎡"
検索: "{住所}" 登記 OR 登記簿 地積
検索: "{施設名}" "敷地面積" OR "延床面積" OR "坪"
検索: site:reinfolib.mlit.go.jp "{町名}"  （不動産取引価格情報）
```

- 建築確認申請の概要書（自治体の建築計画概要書閲覧サービス）にも敷地面積が記載される場合がある
- 固定資産税の課税明細は非公開だが、不動産鑑定評価書や裁判記録に地積が載る場合がある

#### 4.5b: Google Maps 衛星写真からの面積測定

Web検索で面積が見つからない場合、MCP Playwright で Google Maps を開き、衛星写真から敷地の概算面積を測定する。

```
手順:
1. mcp__playwright__browser_navigate で Google Maps の衛星写真を開く
   URL: https://www.google.com/maps/@{lat},{lon},18z/data=!3m1!1e1
2. 「距離を測定」機能で敷地外周をポリゴン選択し面積を読み取る
   - 右クリック → 「距離を測定」 → 敷地境界をクリックしてポリゴンを閉じる
3. 表示された面積（m²）を記録する
```

- 測定精度は ±10〜20% 程度。`area_m2_source: Google Maps衛星写真からの概算測定` と記録する
- Playwright が使えない場合は、敷地の概算寸法（東西×南北）から矩形近似で推定する

### 3.5 住所の正規化

パッチファイルに登録する前に、住所を以下の形式に正規化する：

```
東京都{区市町村}{町名}{丁目}{番}{号}
```

- 全角数字 → 半角数字（例：「３丁目」→「3丁目」）
- 漢数字 → アラビア数字（例：「三丁目」→「3丁目」）
- ハイフン形式も可（例：「東京都港区六本木3-4-33」）
- 郵便番号は含めない
- ビル名・階数は含めない（土地のジオコーディングには不要）
- 「東京都」から始めること

**良い例:**

```
東京都中央区日本橋1丁目15番3号
東京都港区六本木3-4-33
東京都足立区千住橋戸町31番
```

**悪い例:**

```
中央区日本橋1-15-3          # 「東京都」が無い
東京都中央区日本橋           # 番地が無い
〒100-0001 東京都千代田区... # 郵便番号が含まれている
東京都港区六本木ヒルズ       # ビル名で番地が無い
```

## 4. 判定

検証結果に基づき、各事業所について以下のいずれかに判定する：

| 判定               | 説明                                                       | アクション                 |
| ------------------ | ---------------------------------------------------------- | -------------------------- |
| **確認済み**       | 合算なし、住所も正確                                       | → 現住所をそのままYAML登録 |
| **過大評価の疑い** | [BAD_PATTERN_1](#bad-pattern-1) に該当（合算・面積不整合） | → 分割した住所をYAML登録   |

> **重要**: 判定結果に関わらず、**全事業所の住所を必ずパッチファイルに登録する**。

### 判定フローチャート

```
対象企業の全事業所を確認
  │
  ├─ 事業所名に「他」「及び」→ BAD_PATTERN_1（合算の疑い）
  │   └─ 注入済みテキスト確認 → 拠点分解 → 分割した住所をYAML登録
  │
  ├─ 面積≥10,000m² かつ都心住所 → BAD_PATTERN_1（立地の妥当性確認）
  │   └─ 正しい住所をYAML登録
  │
  └─ 上記に該当しない → 現在の住所をそのままYAML登録
```

## 5. パッチファイルへの書き出し

**このセクションは必ず実行する。** 調査結果はパッチファイルに書き出さなければ失われる。

### 5.1 ジオコード検証

登録する住所が `gaiku` レベルでジオコーディングできるか確認する：

```python
from src.geocode_tokyo import TokyoGeocoder

geocoder = TokyoGeocoder(
    oaza_csv="data/geocoding/geocode_ref_oaza_chome_tokyo_2024/13_2024.csv",
    gaiku_csv="data/geocoding/geocode_ref_gaiku_tokyo_2024/13_2024.csv",
)

addr = "東京都足立区宮城1丁目35番18号"
lat, lon, level = geocoder.geocode(addr)
print(f"{addr} → {level} ({lat}, {lon})")
# 期待: "gaiku" と表示されること
```

**全住所のジオコード結果を確認してからパッチファイルに書き出すこと。**

### 5.2 ファイル構造

パッチファイル `config/address_patches/{証券コード}.yaml` に以下の形式で**新規作成**する。
パッチファイルは `parallel_research.py` が実行開始時にディレクトリをクリアし、各プロセスが新規作成する。完了後 `merge_address_patches.py` で `address_overrides.yaml` に一括マージされる。

```yaml
"****":
  本社: 東京都中央区日本橋2丁目7番1号
  東京支店: 東京都江東区有明4丁目3番22号
```

面積合算を分割する場合は、`list` 形式を使う:

```yaml
"****":
  本社:
    - name: 本社(九段北)
      address: 東京都千代田区九段北4丁目3番29号
      area_m2: 231.0
      area_m2_is_estimated: true
      area_m2_source: 公示地価標準地の近傍地積による推定
      area_m2_source_url: https://www.reinfolib.mlit.go.jp/
      area_m2_note: 九段北4丁目8番37外(地積231㎡)を近傍代理値として採用
    - name: 本社(全国貸与資産・合算)
      address: 全国各所
      area_m2: 564750.0
      area_m2_is_estimated: false
```

### 5.2.1 `area_m2` 推定運用（変更点）

- 東京側エントリを `0` に固定しない。可能な限り推定値を入れる。
- 推定時は `area_m2_is_estimated: true` とし、`area_m2_source` を必須で記録する。
- 根拠探索の優先順位は以下:
  1. 登記簿（地積）
  2. 有報の固定資産注記・設備注記（面積内訳）
  3. 公示地価標準地の近傍地積による推定

### 5.3 登録ルール

- **事業所名は出力CSVの値と完全一致させる**（スペース含む）
  - 例: 出力CSVが「本社 他」なら、YAMLのキーも `本社 他` にする
  - 例: 出力CSVが「本社他」なら `本社他` にする
- **証券コードはクォート付き文字列として記載**（`'****':` の形式）
- **対象企業の全事業所を登録する**

### 5.4 書き出し後の確認

パッチファイルに書き出したら、内容を `cat` で表示して正しく書き出されたことを確認する：

```bash
cat config/address_patches/****.yaml
```

### 5.5 推論根拠の保存（必須）

分割時に `area_m2` を推定した場合は、推論根拠を必ず `split-address/{証券コード}.md` に保存する。

- ファイル名は証券コード固定（例: `split-address/****.md`）
- 既存ファイルがある場合は追記ではなく更新し、最新の判断を残す
- URLを含む根拠は最低2系統（有報 + 登記/IR/公的データのいずれか）を記載
- 根拠の取得日・推論式・最終配分面積を明記する

推奨フォーマット:

```md
# {証券コード} split-address 推論メモ

## 1. 対象

- 証券コード: {証券コード}
- 企業名: {企業名}
- 対象事業所: {事業所名}
- 更新日: YYYY-MM-DD

## 2. 元データ

- 元の土地面積: {N} m2
- 元住所: {住所}
- 問題点: {都心大面積/合算注記 など}

## 3. 根拠ソース

| 種別 | 取得日 | 要点 | URL |
| ---- | ------ | ---- | --- |
```

## 6. 注意事項

- **集約名の事業所**（「本社他」「本社・○○」「○○等」）は、複数の土地が1行に集約されている。代表的な住所（通常は本社住所）を設定する。
- **移転情報に注意** — 検索で見つかる住所が最新でない場合がある。有報の事業年度末時点の住所であることを確認する。
- **`SKILL.md` は更新しない**
